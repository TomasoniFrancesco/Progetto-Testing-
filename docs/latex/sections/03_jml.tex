\section{JML e verifica statica (ESC)}
\label{sec:jml-ref}

Per la parte di design by contract ho annotato con JML la classe \texttt{Parcheggio}
(package \texttt{it.tvsw.smartparking.core}), che è il nucleo puro del dominio: tiene i
contatori dei posti liberi e gestisce l'assegnazione e il rilascio, cioè la stessa
logica delle regole \texttt{r\_gestione\_VER}, \texttt{r\_gestione\_INGR} e
\texttt{r\_gestione\_USC} del modello ASM. L'ho tenuta piccola apposta e senza
dipendenze esterne (dentro ci sono solo \texttt{int} ed enum), proprio perché così
OpenJML riesce a dimostrarla tutta in modalità Extended Static Checking. Come chiedeva
la consegna, il resto del sistema (la FSM, la UI Vaadin, il display, i sensori) è Java
normale, senza nessuna annotazione JML.

Un dettaglio sulla visibilità: i campi \texttt{postiStd} e \texttt{postiDis} li ho
dichiarati \texttt{private /*@ spec\_public @*/}. Il motivo è che le clausole di
specifica public, come le invarianti e le postcondizioni, possono nominare solo cose
visibili a livello di specifica public; senza lo \texttt{spec\_public} OpenJML si
lamenta con un errore di visibilità.

\subsection{Invarianti}

Ho scritto due invarianti di classe, che devono valere in ogni stato osservabile
dell'oggetto, cioè da dopo il costruttore in poi:

\begin{itemize}
\item il numero di posti standard liberi è sempre compreso tra 0 e la capacità
massima \texttt{MAX\_STD};
\item il numero di posti disabili liberi è sempre compreso tra 0 e la capacità
massima \texttt{MAX\_DIS}.
\end{itemize}

In pratica sono la versione Java delle proprietà di safety che avevo già verificato con
il model checking sul modello ASM (\texttt{ag(posti >= 0)} e \texttt{ag(posti <= 1)},
si veda \S\ref{sec:asmetav-vc}). Così la stessa proprietà finisce per essere garantita
su tre livelli: il modello, il contratto e i test.

\begin{lstlisting}[style=terminal, caption={Invarianti di classe}]
//@ public invariant 0 <= postiStd && postiStd <= MAX_STD;
private /*@ spec_public @*/ int postiStd;

//@ public invariant 0 <= postiDis && postiDis <= MAX_DIS;
private /*@ spec_public @*/ int postiDis;
\end{lstlisting}

\subsection{Costruttori}

Per i costruttori ho scritto questi contratti:

\begin{itemize}
\item il costruttore di default garantisce (\texttt{ensures}) lo stato iniziale del
modello ASM: tutti i posti liberi (\texttt{postiStd == MAX\_STD},
\texttt{postiDis == MAX\_DIS});
\item il costruttore con parametri (usato nei test combinatori e MC/DC per
costruire configurazioni arbitrarie) \emph{richiede} (\texttt{requires}) che i
valori iniziali siano già dentro i limiti dell'invariante, e garantisce che i campi
vengano inizializzati esattamente con i valori passati;
\item la violazione della precondizione è anche gestita difensivamente a runtime
con \texttt{IllegalArgumentException}, comportamento verificato in
\texttt{ParcheggioTest} con \texttt{assertThrows}.
\end{itemize}

\begin{lstlisting}[style=terminal, caption={Contratti dei costruttori}]
//@ ensures postiStd == MAX_STD && postiDis == MAX_DIS;
public Parcheggio() { ... }

//@ requires 0 <= postiStdIniziali && postiStdIniziali <= MAX_STD;
//@ requires 0 <= postiDisIniziali && postiDisIniziali <= MAX_DIS;
//@ ensures postiStd == postiStdIniziali && postiDis == postiDisIniziali;
public Parcheggio(int postiStdIniziali, int postiDisIniziali) { ... }
\end{lstlisting}

\subsection{Metodo \texttt{assegnaPosto}}

Questo è il metodo con il contratto più corposo, perché deve rispecchiare tutta la
logica di assegnazione di \texttt{r\_gestione\_VER}. I contratti sono questi:

\begin{itemize}
\item viene richiesto che l'utente non sia \texttt{null};
\item per gli utenti STD e ABBONATO la postcondizione descrive i due esiti
possibili in funzione dello stato \emph{precedente} (\texttt{\textbackslash old}):
se c'era un posto standard libero il risultato è \texttt{POSTO\_STD} e il contatore
è decrementato di 1; altrimenti il risultato è \texttt{NESSUNO} e nulla cambia;
\item per gli utenti DISABILE la postcondizione descrive i tre esiti possibili:
posto disabile se disponibile; altrimenti \emph{fallback} su un posto standard se
disponibile; altrimenti \texttt{NESSUNO} senza modifiche;
\item in ogni esito viene anche vincolato che il contatore ``dell'altro'' tipo di
posto resti invariato: la postcondizione è cioè \emph{completa}, non lascia
comportamenti sottospecificati.
\end{itemize}

\begin{lstlisting}[style=terminal, caption={Contratto di assegnaPosto}]
//@ requires utente != null;
//@ ensures (utente == TipoUtente.STD || utente == TipoUtente.ABBONATO) ==>
//@     ((\old(postiStd) > 0 && \result == TipoPosto.POSTO_STD
//@       && postiStd == \old(postiStd) - 1 && postiDis == \old(postiDis))
//@      || (\old(postiStd) == 0 && \result == TipoPosto.NESSUNO
//@       && postiStd == \old(postiStd) && postiDis == \old(postiDis)));
//@ ensures utente == TipoUtente.DISABILE ==>
//@     ((\old(postiDis) > 0 && \result == TipoPosto.POSTO_DIS
//@       && postiDis == \old(postiDis) - 1 && postiStd == \old(postiStd))
//@      || (\old(postiDis) == 0 && \old(postiStd) > 0
//@       && \result == TipoPosto.POSTO_STD
//@       && postiStd == \old(postiStd) - 1 && postiDis == \old(postiDis))
//@      || (\old(postiDis) == 0 && \old(postiStd) == 0
//@       && \result == TipoPosto.NESSUNO
//@       && postiStd == \old(postiStd) && postiDis == \old(postiDis)));
public TipoPosto assegnaPosto(TipoUtente utente) { ... }
\end{lstlisting}

\subsection{Metodo \texttt{liberaPosto}}

Questo metodo corrisponde al rilascio del posto della regola \texttt{r\_gestione\_USC}.
I contratti sono questi:

\begin{itemize}
\item viene richiesto che il posto non sia \texttt{null};
\item viene richiesto che il contatore corrispondente al posto da liberare non sia
già al massimo: senza questa precondizione l'incremento violerebbe l'invariante
superiore (non si possono ``inventare'' posti oltre la capacità);
\item le postcondizioni garantiscono l'incremento di 1 del solo contatore
corrispondente, e che con \texttt{NESSUNO} lo stato resti del tutto invariato.
\end{itemize}

\begin{lstlisting}[style=terminal, caption={Contratto di liberaPosto}]
//@ requires posto != null;
//@ requires posto == TipoPosto.POSTO_STD ==> postiStd < MAX_STD;
//@ requires posto == TipoPosto.POSTO_DIS ==> postiDis < MAX_DIS;
//@ ensures posto == TipoPosto.POSTO_STD ==>
//@     postiStd == \old(postiStd) + 1 && postiDis == \old(postiDis);
//@ ensures posto == TipoPosto.POSTO_DIS ==>
//@     postiDis == \old(postiDis) + 1 && postiStd == \old(postiStd);
//@ ensures posto == TipoPosto.NESSUNO ==>
//@     postiStd == \old(postiStd) && postiDis == \old(postiDis);
public void liberaPosto(TipoPosto posto) { ... }
\end{lstlisting}

\subsection{Metodi getter}

I due getter li ho annotati \texttt{/*@ pure @*/}, cioè senza effetti collaterali: è la
condizione che serve per poterli usare dentro le clausole JML. La postcondizione dice
solo che restituiscono il valore del campo, niente di più.

\begin{lstlisting}[style=terminal, caption={Getter puri}]
//@ ensures \result == postiStd;
public /*@ pure @*/ int getPostiStd() { ... }

//@ ensures \result == postiDis;
public /*@ pure @*/ int getPostiDis() { ... }
\end{lstlisting}

\subsection{Verifica dei contratti con OpenJML (ESC)}

Una volta scritti i contratti li ho verificati staticamente con OpenJML (release
21.0.27, build nativa per macOS arm64) in modalità \texttt{--esc}. Per ogni metodo il
tool traduce codice e contratti in formule logiche e chiede al solver Z3 di dimostrare
che \emph{ogni} esecuzione possibile rispetta postcondizioni e invarianti; è un
controllo più forte del testing, che invece guarda solo alcuni casi. Il comando, dalla
root del progetto, è questo:

\begin{lstlisting}[style=terminal, caption={Comando di verifica ESC}]
$ openjml --esc --progress \
    -cp java/src/main/java \
    java/src/main/java/it/tvsw/smartparking/core/Parcheggio.java
\end{lstlisting}

\subsubsection*{Un contratto che inizialmente non chiudeva}

Arrivare a ``tutti Verified'' non è stato immediato. Alcuni contratti, nella loro
prima stesura, venivano rifiutati dal solver, e vale la pena mostrare perché e come
sono stati corretti: è lo stesso tipo di ostacolo che rende difficile la chiusura ESC
su codice con aritmetica non vincolata.

Il caso più chiaro è \texttt{liberaPosto}. Nella versione iniziale la postcondizione
descriveva l'incremento del contatore, ma \emph{mancava la precondizione} che vieta
di liberare un posto quando il contatore è già al massimo:

\begin{lstlisting}[style=terminal, caption={Prima versione di liberaPosto (senza il requires di capacità)}]
//@ requires posto != null;
//@ ensures posto == TipoPosto.POSTO_STD ==>
//@     postiStd == \old(postiStd) + 1 && postiDis == \old(postiDis);
public void liberaPosto(TipoPosto posto) { ... }
\end{lstlisting}

Con questo contratto, OpenJML esplora anche lo stato \texttt{postiStd == MAX\_STD}:
in quel caso \texttt{postiStd + 1} vale \texttt{MAX\_STD + 1}, che \emph{viola
l'invariante di classe} \texttt{postiStd <= MAX\_STD}. Il solver non riesce quindi a
ristabilire l'invariante all'uscita del metodo e segnala l'errore:

\begin{lstlisting}[style=terminal, caption={Errore ESC sulla prima versione}]
Parcheggio.java:.. warning: The prover cannot establish an assertion
   (InvariantExit) in method liberaPosto
   postiStd == \old(postiStd) + 1 ...
   Associated declaration: invariant 0 <= postiStd && postiStd <= MAX_STD
\end{lstlisting}

È lo stesso ostacolo (un'operazione aritmetica che può ``sforare'' un limite) per cui
su un dominio più ricco, con array e contatori non limitati, la chiusura completa
diventa molto difficile. Qui la soluzione è rafforzare la precondizione, in modo che
il chiamante garantisca lo spazio per l'incremento:

\begin{lstlisting}[style=terminal, caption={Versione corretta: il requires di capacità chiude la prova}]
//@ requires posto == TipoPosto.POSTO_STD ==> postiStd < MAX_STD;
//@ requires posto == TipoPosto.POSTO_DIS ==> postiDis < MAX_DIS;
\end{lstlisting}

Con \texttt{postiStd < MAX\_STD} assunto all'ingresso, dopo l'incremento vale
\texttt{postiStd <= MAX\_STD} e l'invariante è ristabilita: il metodo passa a
\emph{Verified}. È proprio questa disciplina, cioè vincolare via
\texttt{requires} o invariante tutto ciò che entra in un'operazione aritmetica, che
permette a \texttt{Parcheggio} di chiudere tutti i contratti, cosa che su un nucleo con
interi liberi non sarebbe possibile. Un secondo ostacolo, di natura diversa, era di
pura visibilità JML: i campi \texttt{private} referenziati da clausole \texttt{public}.
L'ho risolto con \texttt{spec\_public}, come descritto nella nota a inizio sezione.
